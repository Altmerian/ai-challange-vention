# Task 4 — "MCPing" Submission Report

A Model Context Protocol server (`task-4/server/`) for Air Traffic Control system that schedules airport arrivals and departures across configurable runways / gates / ground crew and exposes the schedule to MCP clients over stdio. Six tools (`submit_flight`, `generate_schedule`, `cancel_flight`, `get_airport_status`, `analyze_bottleneck`, `reset_state`) plus three `atc://` resources (`atc://queue`, `atc://runways`, `atc://timeline`). All state is in-memory; restart wipes it.

Check the [README.md](./README.md) for installation, configuration, MCP-client connection examples, and ready-to-copy commands that validate the three brief scenarios. Domain glossary lives in [`CONTEXT.md`](./CONTEXT.md); the full design rationale is in [`PRD.md`](./PRD.md) and [`docs/adr/`](./docs/adr/); the Inspector-driven verification contract is in [`AGENTS.md`](./AGENTS.md).

### Implementation stack

- TypeScript (strict mode, `exactOptionalPropertyTypes: true`) on Node.js ≥ 20.
- [`@modelcontextprotocol/sdk`](https://github.com/modelcontextprotocol/typescript-sdk) for the MCP server, client, and `StdioServerTransport`.
- [`zod`](https://zod.dev/) (`z.strictObject`) for every tool's input schema — unknown fields are rejected at the protocol boundary.
- `vitest` for unit tests (deep modules in isolation) and integration tests (full MCP protocol via the SDK's `InMemoryTransport`).
- [MCP Inspector](https://modelcontextprotocol.io/docs/tools/inspector) for end-to-end verification through real stdio. The canonical entry point is `npm run verify:inspector`, an SDK-client harness that drives the freshly built `dist/index.js` and asserts every protocol-level check + scenario from `AGENTS.md`.

## Scheduling approach and key decisions behind it

The scheduler is a **greedy, dependency-respecting, priority-ordered placer** with deterministic output. The decisions below explain why each piece is shaped the way it is; the full reasoning lives in the ADRs linked from each bullet.

- **Greedy, not optimal.** A scheduling pass builds the dependency DAG, then loops: pick the **ready** flight (every predecessor placed) with the highest priority — tiebreaking by lowest submission index — and reserve its earliest feasible window across compatible runways and any gate / ground-crew unit. No displacement of placed flights; no priority inheritance up dependency chains. A high-priority flight that cannot fit becomes `unscheduled` rather than bumping a lower-priority neighbour. The brief asks for *correct and priority-respecting*, not *optimal*; greedy gives transparent, explainable, deterministic placements that an AI client can reason about ([ADR-0001](./docs/adr/0001-scheduling-algorithm.md)).
- **Integer-minute time with a UTC anchor and per-call IANA timezone.** All durations, buffers, horizons, and offsets are non-negative integer minutes. Each pass captures `schedule_start_at` once as a UTC ISO-8601 instant (minute precision); every operation's canonical position is `start_offset_min` / `end_offset_min` against that anchor. Tool responses additionally emit `start_at` / `end_at` formatted in the client's IANA zone — but the underlying schedule is timezone-free. Determinism tests compare offsets, not wall-clock strings. Invalid IANA names return an error envelope, never a silent UTC fallback ([ADR-0002](./docs/adr/0002-time-and-timezone-model.md)).
- **Bottleneck = longest path by elapsed minutes (CPM critical path), not node count.** A 2-flight chain straddling a 4-hour gate turnaround is a bigger bottleneck than a 5-flight chain of 2-minute hops. Tiebreaks: elapsed → node count → earliest first-flight start → lex flight-number sequence. The report exposes both `cumulative_operation_min` and `cumulative_wait_min` so clients can attribute the delay; the wait field folds dependency-buffer waits and resource-contention gaps together because greedy scheduling cannot cleanly separate them ([ADR-0003](./docs/adr/0003-bottleneck-by-elapsed-minutes.md)).
- **Forward-reference dependencies are allowed; unknown predecessors fail at schedule time.** `submit_flight` accepts a `dependencies` list naming flights that may not yet exist. Resolution happens during the next scheduling pass; an unresolved predecessor produces `unscheduled` with reason `dependency_missing` and the offending flight in `blocking_flight_number`. Self-references are the one exception — rejected at submission with reason `self_dependency`. The alternative (rejecting submissions naming unknown predecessors) would force users to topologically sort their submissions, which is hostile to the natural "wire up a multi-leg journey" workflow ([ADR-0004](./docs/adr/0004-forward-reference-dependencies.md)).
- **Layered unscheduled-reason taxonomy.** Direct missing/cancelled predecessors → `dependency_missing` / `dependency_cancelled` with `blocking_flight_number` = the offending predecessor. Cycle members → `dependency_cycle` (no `blocking_flight_number`; `detail` lists the cycle). Everything downstream — transitive descendants of any of the above, plus descendants of `no_compatible_runway` / `horizon_exceeded` flights — → `dependency_unscheduled` with `blocking_flight_number` = the first unscheduled predecessor. Each failure mode is reported with full fidelity at the same level.
- **Cancellation auto-regenerates the schedule.** `cancel_flight` flips the flight to `cancelled` (terminal, idempotent) *before* invoking the scheduler, so direct dependents emit `dependency_cancelled` in the same round-trip — no follow-up `generate_schedule` is required. Flight-number uniqueness survives cancellation: a cancelled number can never be resubmitted.
- **In-memory state, explicit reset.** No persistence. `reset_state` wipes the queue, the schedule, and the submission-index counter — the in-process equivalent of restarting the server. Configuration is read once at startup; to change it, restart the process.
- **Strict input schemas at the wire boundary.** Every tool advertises a `z.strictObject` input schema (`additionalProperties: false`). Unknown fields are rejected by the SDK before the handler runs. Business-rule failures (duplicate flight number, self-dependency, invalid IANA timezone) come back as MCP `isError: true` envelopes that collect **every** problem found, not just the first.

## What worked

- **The PRD + CONTEXT.md + ADR triplet kept iteration grounded.** Naming was settled first via `/grill-with-docs`, then crystallised into `PRD.md`. Whenever a slice surfaced an ambiguity, the answer lived in the glossary or the relevant ADR — not in someone's head — so revisiting a slice after a few days never required re-deriving terminology.
- **Tracer-bullet slices.** Nine vertical slices, each cutting through schema → state/scheduler → MCP surface → tests, each independently demoable. Every slice closed only after its Inspector-driven check went green, which kept regressions out of `main`.
- **Deep modules as pure functions.** `Scheduler`, `BottleneckAnalyzer`, `TimezoneFormatter`, and `airport-status` are all `(inputs) → outputs` with no I/O, no env access, no clock. Unit tests pinned them with hand-built fixtures; determinism replays diffed the projected snapshots byte-for-byte; the shallow `McpServer` handler layer became thin wiring with nothing meaningful to mock.
- **The Inspector-driven harness (`npm run verify:inspector`) The harness now drives the freshly-built `dist/index.js` and runs all three brief scenarios + protocol checks + a determinism replay in one go.
- **Adversarial review via `/codex:adversarial-review` on each slice.** Codex (gpt-5-5 xhigh) acting as second-opinion reviewer pushed back hardest on the stability claim (see "What didn't"), the cascade-vs-reason layering, and the wisdom of folding the trailing separation buffer into runway `busy_minutes` (kept, on PRD-stated grounds; rejected adding the same trailing buffer to gates).

## What didn't / what we deliberately left out

- **The "cancel leaves unrelated flights stable" invariant had to be narrowed.** Initial design claimed any cancel left all other offsets byte-identical. Adversarial review pointed out that greedy scheduling can reclaim a freed slot earlier for a contested lower-priority flight — so the claim is only true when the cancelled flight has no dependents *and* its runway/gate slot is uncontested. The narrow invariant is now the only one tested, against a deliberately uncontested fixture.
- **`cumulative_wait_min` cannot cleanly separate dependency-buffer waits from resource-contention gaps.** Both manifest as gaps between a predecessor's end and a dependent's start, and splitting them apart would require a counterfactual "what if no contention" re-run of the scheduler. Folded together by design; clients that need to attribute wait time compare against `ATC_DEPENDENCY_BUFFER_MIN × (chain_length − 1)`.
- **Two validation paths by design.** Schema validation goes through the SDK (`isError: true` with text-formatted zod issues from the strict input schema); business-rule failures go through our `errorEnvelope` (`{errors: ValidationIssue[]}` JSON). Routing the schema errors through the same envelope would force dropping `inputSchema` from `registerTool` and losing the strict-schema advertisement in `tools/list` — a trade-off where catalogue accuracy beat envelope-format uniformity.
- **Deliberately out of scope** (see [PRD § Out of Scope](./PRD.md#out-of-scope) for the full list): persistence of any kind, authentication / multi-tenancy, streamable HTTP transport, optimal scheduling, wall-clock execution simulation, a `completed` flight state, per-gate or per-crew attributes, per-runway attributes beyond `length_m`, per-edge dependency buffer, priority inheritance, displacement, update / resurrection semantics on flight numbers, dynamic configuration changes, UI / dashboard / web frontend, performance and load testing, snapshot / property-based testing.
- **MCP Inspector** UI bug with resource fetching: if you fetch a resource, then re-run the same scenario that triggers the same resource fetch, the Inspector's UI doesn't update the attached resource payload on the second fetch. The workaround is to capture the Inspector's CLI transcript (which includes the full payload on every fetch) and assert against that, instead of relying on the UI's "Resources" tab.
